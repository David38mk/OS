## Задача 1.

Да се напише Python скрипта која како прв аргумент добива име на влезна датотека. Доколку скриптата се повика без аргументи, да заврши со порака за грешка. Влезната датотека е access log од веб сервер, во која секоја линија го има следниот формат:


1. За секој различен статус код да отпечати колку барања имало со тој статус и колку бајти се испратени вкупно, а на крај вкупниот број на барања и бајти за целата датотека.
2. Да ги отпечати трите IP адреси со најмногу барања, подредени опаѓачки.
3. Да ги најде „сомнителните“ IP адреси: тоа се адреси кои во една иста минута направиле повеќе од N барања. N е вториот, опционален аргумент од командна линија; доколку не е наведен, N е 10. За секоја сомнителна адреса се печати колку барања направила и во која минута.

## Задача 2.

Да се напише C програма која проверува дали повеќе хостови (сервери) се достапни, истовремено. Хостовите (IP адреси или имиња) се внесуваат како аргументи од командна линија и нивниот број е променлив. Доколку програмата се повика без аргументи, да заврши со порака за грешка.

Родител процесот најпрво од тастатура вчитува колку секунди (T) најмногу смее да трае една проверка. Потоа за секој хост креира по едно дете, а секое дете ја извршува наредбата `ping -c 1 <хост>`. Родителот не чека бесконечно: доколку некое дете не заврши за T секунди, родителот го прекинува (убива).

Кога ќе завршат сите деца, родителот за секој хост, во редоследот во кој се наведени, печати една линија со резултат и со времето во секунди колку траела проверката:

- `UP` – доколку наредбата завршила успешно (излезен статус 0),
- `DOWN` – доколку наредбата завршила со грешка (излезен статус различен од 0),
- `TIMEOUT` – доколку родителот морал да го прекине детето.

На крај родителот ја испишува пораката: „Zavrshuva process 0“.

*Напомена:* за чекање на дете без блокирање може да се користи `waitpid` со `WNOHANG`, за прекинување `kill`, а излезот на `ping` во дете процесот може да се исклучи со `freopen("/dev/null", "w", stdout)` пред извршувањето на наредбата.

**Пример:**

```
./z2 8.8.8.8 feit.ukim.edu.mk nepostoi.local 10.255.255.1
Vnesi timeout vo sekundi: 2
8.8.8.8 UP (0 s)
feit.ukim.edu.mk UP (0 s)
nepostoi.local DOWN (0 s)
10.255.255.1 TIMEOUT (2 s)
Zavrshuva process 0
```

**БОНУС1:** доколку првиот аргумент е `-r` проследен со број M, тогаш секој хост што е DOWN се проверува повторно, најмногу M пати, со пауза од една секунда меѓу обидите. Во резултатот за тој хост дополнително се печати по колку обиди станал UP, или дека останал DOWN по M обиди.

```
./z2 -r 3 8.8.8.8 nepostoi.local
Vnesi timeout vo sekundi: 2
8.8.8.8 UP (0 s)
nepostoi.local DOWN (0 s) posle 3 obidi
Zavrshuva process 0
```

**БОНУС2:** дали чекањето на дете процесите може да се направи со нитки, по една нитка за секое дете, наместо со една јамка во родителот? Што се добива, а што се губи со тој пристап?

## Решенија

| Датотека | Содржина |
|---|---|
| `Z1.py3` | Задача 1: `readlines()` + `split()`, без регуларни изрази |
| `Z1_S.py3` | Задача 1, целосна верзија: регуларен израз за препознавање на линијата (издржува и патека со празно место); ист излез |
| `Z2.c` | Задача 2: сè во `main`, низи наместо структури, време со `time()`, без БОНУС1. Споредбата е `> T`, не `>= T`, бидејќи `time()` брои цели секунди и `>=` би убивало до една секунда предвреме |
| `Z2_S.c` | Задача 2 и БОНУС1 (`-r M`), целосна верзија: помошна функција за една рунда, структура по хост, монотон часовник; ист излез |
| `Z2_threads.c` | БОНУС2: истата проверка, но чекањето го прават нитки, по една за секое дете |
| `tests/run_tests.sh` | тестови за сè погоре; се пушта во Linux кутијата (`ssh oslab`) |
| `portal/` | материјали за студентите: `access.log` и очекувани излези, поголем `access_golem.log` со свои излези, `zadacha2upatstva.txt` |
| `_gen/make_log.py` | детерминистички го генерира `portal/` и очекуваните излези со помош на `Z1.py3` |

Извршување, во Linux кутијата од оваа папка:

```bash
python3 Z1.py3 portal/access.log 3 -b
gcc -Wall -Wextra Z2.c -o Z2 && ./Z2 127.0.0.1 nepostoi.example 192.0.2.1
gcc -Wall -Wextra -pthread Z2_S.c -o Z2_S && ./Z2_S -r 3 127.0.0.1 nepostoi.example 192.0.2.1
gcc -Wall -Wextra -pthread Z2_threads.c -o Z2_threads && ./Z2_threads 127.0.0.1 192.0.2.1
bash tests/run_tests.sh
```

Тестовите за задача 2 не користат мрежа: во привремена папка ставаат свој `ping` (скрипта) пред вистинскиот во `PATH`, кој за `up.test` излегува со 0, за `down.test` со 2, а за `slow.test` спие 30 секунди. Програмата не знае за тоа, бидејќи `execlp` го бара `ping` низ `PATH`.

**Конвенции кои текстот не ги фиксира, а решението и очекуваните излези ги користат:** статус кодовите се печатат растечки; топ 3 е опаѓачки по број барања, при изедначување по редослед на прво појавување; сомнителните адреси се по редослед на прво појавување во логот; `-r M` значи вкупно M обиди, како во примерот од текстот (`-r 3` → „posle 3 obidi“).

**Одговор на БОНУС2.** Да за чекањето, не за извршувањето. Нитките живеат во родителот, па `waitpid` од нитка работи: секоја нитка блокира на своето дете, а еден тајмер во главната нитка по T секунди ги убива децата што уште не завршиле. Се добива код без анкетирање (polling), едноставна логика по дете и точен тајмаут од едно место. Се губи: споделените податоци бараат mutex, `fork` мора да се повика пред да се создадат нитките (fork го дуплира само процесот со нитката што го повикала, другите нитки и нивните заклучувања исчезнуваат во детето), и има повеќе код. Самите наредби не можат да бидат нитки: `exec` го заменува целиот процес заедно со сите негови нитки, па `ping` секогаш мора да е посебен процес.
